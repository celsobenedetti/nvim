# hunk diff viewer in a Neovim tabpage

[hunk](https://www.hunk.dev/docs/) is a terminal diff viewer. `:Hunk` /
`<leader>hu` (`after/plugin/hunk.lua`) runs `hunk diff` as a terminal job in
its own tabpage, the lazygit tab pattern (`after/plugin/lazygit.lua`), and
wires hunk's "edit this file" command back into the Neovim that started it: the
file opens in the **first tabpage**, where the code is, instead of nesting an
editor inside hunk's terminal.

## `:Hunk [args]`

Everything after the command name goes straight to `hunk diff`:

| Command          | Runs                 | Reviews                        |
| ---------------- | -------------------- | ------------------------------ |
| `:Hunk`          | `hunk diff`          | working tree (incl. untracked) |
| `:Hunk --cached` | `hunk diff --cached` | the index (alias: `--staged`)  |
| `:Hunk HEAD~1`   | `hunk diff HEAD~1`   | working tree vs that revision  |

Args are not validated: anything `hunk diff` takes (`--watch`, `--mode
unified`, paths) works, and hunk reports what it rejects. An empty review (say
`--cached` with nothing staged) renders as `No files match the current filter.`
and its `e` answers `No file selected.` — hunk is fine, the diff is empty.

Each invocation gets its own tabpage, named after it (`hunk`,
`hunk --cached`, `hunk HEAD~1`), and repeating a command jumps to that tab
instead of starting a second viewer. Tab lookup compares the whole name
(`find_tab`) because `lib.tab.find` matches substrings and would hand plain
`:Hunk` the `hunk --cached` tab. When hunk quits (`q`), `on_exit` closes its
tab and wipes the dead terminal buffer.

`e` always opens the file as it is **on disk**, also while reviewing the index
or a revision — hunk resolves the diff path against the repo
(`resolveEditableFilePath`), it does not check out blobs.

## Which hunk key opens the file

`e` — `hunk.review.editSelectedFile`, "open the selected file in your editor".
It uses the line cursor, so it carries the location, not only the file.

**`gf` is not bindable inside hunk.** Its `[keybindings]` table takes single
chords (`modifier+base`), and a multi-character base must be a known named key
(`tab`, `pageup`, …) — `parseKeyChord` in
`packages/hunk/src/extension-api/keys.ts` rejects `"gf"` as `Unknown key`.
There are no two-key sequences. Another single chord is one line in
`~/.config/hunk/config.toml`, keys listed there replace the defaults:

```toml
[keybindings]
"hunk.review.editSelectedFile" = ["e", "f"]
```

## Why the $EDITOR shim is named `nvim`

hunk has no editor config key: `openSelectedFileInEditor`
(`packages/hunk/src/ui/lib/openInEditor.ts`) reads `$EDITOR`, splits it
respecting quotes, and spawns it directly. The line number only comes along
for vi-style editors — `buildEditorCommand` matches `basename($EDITOR)` against
`vim`/`nvim`/`vi` and then appends `+{line} {absolute path}`; anything else
gets the bare path. So `scripts/hunk-editor/nvim` carries that name to be
handed the location, and is referenced by absolute path (keep its directory
off `$PATH`, or its own `nvim` calls would recurse into the shim).

The shim talks to the parent Neovim over `$NVIM`, the server address Neovim
exports into every job it spawns (`:h $NVIM`):

```sh
nvim --server "$NVIM" --remote-expr "v:lua.require'lib.hunk'.open('{path}', {line})"
```

`lib.hunk.open` switches to the first tabpage, `:edit`s the file and moves the
cursor. `--remote-expr` prints its result, hence the `''` return. Single
quotes in the path are doubled by the shim (the Vimscript string escape).

hunk suspends its renderer around any vi-style editor and resumes when the
child exits, which here is as soon as the RPC returns.

## How the client talks back to this Neovim

Nothing here is a special mode: every Neovim already listens for API calls, and
the shim is a small client of that door. Three parts — who listens, how the
child learns the address, what gets said. Line references are to
`~/local/neovim`.

### The host listens by default

At startup Neovim calls `server_init()` (`src/nvim/msgpack_rpc/server.c:35`),
which opens a listening socket. Without `--listen` the address is autogenerated
as `stdpath('run')/nvim.{pid}.0`:

```
/run/user/1000/nvim.721587.0
```

A Unix domain socket (named pipe on Windows; TCP when the address contains a
colon), living in `$XDG_RUNTIME_DIR`, so only this user can connect. Headless
Neovim listens too, which is what makes the tests below possible.

```vim
:echo v:servername     " primary address
:echo serverlist()     " all of them
```

The protocol is msgpack-RPC (`:h RPC`, `:h api`): a method name plus arguments,
the same channel GUIs and `nvim --server` use. The whole API is reachable, so
anything that can open that socket has full control of the editor — relevant
here because the address is handed down to child processes.

Requests run on the **main loop**, in a normal (non-fast) context. That is what
makes `lib.hunk.open` legal: switching tabpages and `:edit` are forbidden in a
fast callback.

### The child learns the address from `$NVIM`

> `$NVIM` is set to `v:servername` by `|terminal|` and `|jobstart()|`, and is
> thus a hint that the current environment is a child of Nvim — `:h $NVIM`

So the `jobstart(..., { term = true })` in `after/plugin/hunk.lua` gives hunk
`$NVIM` for free, and plain env inheritance carries it to the shim, which hunk
— not Neovim — spawns. The shim uses it as its "am I inside Neovim?" test:

```sh
[ -n "$NVIM" ] || exec nvim "+$line" "$@"
```

### `--server … --remote-expr` is one `nvim_eval` request

`nvim --server` is the same binary in client mode:

1. `remote_request()` (`src/nvim/main.c:975`) runs before any UI starts and
   connects with a 500 ms timeout (`channel_connect`, `main.c:966`).
2. It hands the connection and the leftover argv to
   `vim._cs_remote()` (`runtime/lua/vim/_core/editor.lua:1142`).
3. `--remote-expr` is one synchronous request, then exit
   (`editor.lua:1185`):

   ```lua
   local res = tostring(vim.rpcrequest(rcid, 'nvim_eval', args[2]))
   return { result = res, should_exit = true, tabbed = false }
   ```

The sibling flags map to other API calls the same way: `--remote-send` →
`nvim_input` (`editor.lua:1179`), `--remote` / `--remote-tab` →
`nvim_command('[tab] drop <files>')` (`editor.lua:1200`), which is why
`--remote +42 file` works at all — `:drop` accepts a `+cmd`.

The expression is Vimscript, evaluated by the host; `v:lua.require'lib.hunk'`
is the documented bridge into Lua (`:h v:lua`). Two consequences shaped
`lib.hunk.open`:

- `nvim_eval` returns a value and the client **prints** it, hence the `''`
  return — anything else gets splattered onto hunk's diff.
- `rpcrequest` is **synchronous**: the shim exits only after the host has
  switched tabs and opened the file, so hunk's suspend/resume brackets a
  finished operation instead of a race.

### One `e` press, end to end

```
hunk (child of nvim)                     nvim (host, pid 721587)
  spawns $EDITOR = shim                    listening on /run/user/1000/nvim.721587.0
  shim: nvim --server $NVIM --remote-expr …
        connect(socket) ───────────────▶   accept
        nvim_eval("v:lua.require…") ───▶   main loop: tab 1, :edit, cursor
        ◀─────────────────────── ''        reply
        print "" ; exit
  hunk resumes its TUI
```

### From Lua, skip the wrapper

`:h $NVIM` shows the direct form, no `nvim --server` process needed:

```lua
local chan = vim.fn.sockconnect('pipe', vim.env.NVIM, { rpc = true })
vim.rpcrequest(chan, 'nvim_exec_lua', 'return ... + 1', { 41 })
```

The shim is `sh`, so letting `nvim --server` do the msgpack plumbing is the
shorter path. One nearby guardrail: Neovim deliberately refuses `--remote-ui`
against its own `$NVIM` ("Cannot attach UI of :terminal child to its parent",
`main.c:998`) — that applies to attaching a UI, not to the API calls used here.

## Testing

Real hunk, real keystrokes, headless — hunk renders fine without a UI client:

```sh
cd /tmp/hunkrepo   # a git repo with an unstaged change
nvim --headless -u NONE --cmd "set rtp^=/home/celso/projects/nvim" \
  -c "lua _G.lib = require('lib'); _G.state = require('state')" \
  -c "luafile /home/celso/projects/nvim/after/plugin/hunk.lua" \
  -c "Hunk" -c "sleep 6" \
  -c "lua vim.api.nvim_chan_send(vim.bo[vim.fn.bufnr('term://*')].channel, 'jjj')" \
  -c "sleep 1" \
  -c "lua vim.api.nvim_chan_send(vim.bo[vim.fn.bufnr('term://*')].channel, 'e')" \
  -c "sleep 4" \
  -c "lua print(vim.fn.tabpagenr(), vim.api.nvim_buf_get_name(0), vim.fn.line('.'))" \
  -c "qa!"
```

The repo has to actually have changes for the mode under test (`--cached`
needs something staged, plain `:Hunk` needs an unstaged change): an empty
review leaves `e` with nothing selected, which looks exactly like a broken
shim.

Drive this with `-c` commands and `sleep`, never `nvim -l`. In `-l` script mode
the script runs *instead of* the main loop: the socket exists and the shim's
client connects, but the `nvim_eval` is never serviced, so the client waits,
the parent exits, and the orphaned client falls back to starting a real editor
— which then logs `Nvim: Caught deadly signal 'SIGHUP'`.

Sending `q` instead asserts the other half: hunk exits, `on_exit` closes the
tab and wipes the dead terminal buffer.
